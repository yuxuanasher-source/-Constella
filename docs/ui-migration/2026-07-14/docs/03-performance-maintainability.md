# 前端性能与可维护性方案

## 1. 性能预算

| 指标 | 目标 |
|---|---:|
| LCP P75 | <= 2.5s |
| INP P75 | <= 200ms |
| CLS | <= 0.1 |
| 公共壳层客户端 JS | <= 50KB gzip |
| 单页面新增客户端 JS | <= 100KB gzip |
| 首屏客户端 JS | 目标 <= 200KB gzip |
| 像素截图差异 | <= 0.2%，稳定后 <= 0.1% |

预算以迁移前实测为基线。如果现状高于预算，每个迁移页面至少不得倒退，并在完成后逐步收紧。

## 2. 加载策略

- 页面和数据默认由 Server Component 首屏输出。
- Markdown 编辑器、AI 会话工具、图表和大型弹窗使用动态导入。
- 侧栏不自动预取全部大型业务路由；仅在明确 hover/focus 或用户高概率路径上预取。
- 位图使用 `next/image` 并固定宽高。
- 表格默认服务端分页，每页 30-50 条；超过 200 行且确有连续滚动需求时再虚拟化。
- 搜索输入约 250ms 防抖，并取消过期请求。

## 3. 数据和轮询

- 用户、组织和权限相关数据不做跨用户持久缓存。
- 同一次服务端请求允许请求内去重。
- 静态字典和无敏感性的组织配置可使用标签缓存，并在 mutation 后精确失效。
- 轮询归属当前业务页面；页面隐藏时暂停，错误后指数退避。
- 不在公共壳层启动报数、排班、结算和 AI 的全局轮询。
- mutation 完成后只刷新受影响的查询或路由段。

## 4. 状态管理

- URL：筛选、分页、排序、标签页和可分享的选中对象。
- 服务端：首屏业务数据、权限和组织上下文。
- 局部客户端：输入草稿、弹窗开关、行选择和乐观状态。
- Context：仅用于主题、当前组织等低频稳定上下文。
- 禁止建立包含全部页面数据和动作的 `OpsLiveDataProvider`。

## 5. CSS 和组件规则

- 设计值进入 `styles/ops/tokens.css`，组件样式使用 CSS Modules 或现有 Tailwind token。
- 除动态坐标、进度和测量结果外不新增内联样式。
- 公共组件不得读取业务 API。
- 页面文件只负责组合和数据入口，不堆积业务规则。
- DTO 映射只保留一个权威位置，视图不得猜测后端字段。
- 新组件优先可组合 API，不堆叠大量布尔 props。
- 正式图标只用 `lucide-react`；不手写重复 SVG。

## 6. 代码审查警戒线

以下情况必须在 PR 中说明理由或继续拆分：

- 单个新组件超过约 300 行。
- 单个页面同时管理三个以上互不相关的业务状态组。
- 一个 Client Component 包住完整页面但只有少量区域需要交互。
- 新增跨业务 Provider、事件总线或全局 store。
- 新增依赖只是为了一个简单控件。
- 复制原型中的完整 CSS 或模拟数据进入生产组件。

## 7. 监控

- 构建阶段记录每个路由的 JS chunk 变化。
- Playwright 记录关键页面的 Web Vitals 和截图。
- 灰度阶段观察客户端异常率、API 失败率、路由加载时间和高风险动作失败率。
- 性能倒退或错误率明显上升时通过功能开关回到旧页面。
