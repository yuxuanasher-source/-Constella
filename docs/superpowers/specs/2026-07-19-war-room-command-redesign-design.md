# 智能作战台重塑设计：今日指挥台

日期：2026-07-19

## 结论

智能作战台不再做成“AI 功能集合页”或概念化大屏，而是重塑为经营舱风格的今日指挥台：第一屏回答运营当天最关心的三个问题：

1. 现在最应该先处理什么？
2. 为什么它排在前面，证据来自哪里？
3. 点下一步后进入哪个真实业务闭环？

视觉和交互基准来自 `constella-ui-migration-kit-2026-07-14.zip`，尤其是：

- `frontend-design/source/index.html`：经营总览、行动队列和运营壳层。
- `frontend-design/source/ai-workbench.html`：AI 会话、上下文、产物和安全网关。
- `frontend-design/source/operations.css`：Arco 风格 token、浅灰壳层、6px 卡片、密集表格。
- `docs/02-pixel-design-spec.md`：字体、圆角、颜色、响应式和像素验收。
- `docs/04-page-route-data-map.md`：`/console` 与 `/console/ai` 的数据域分工。

## 产品定位

### 不是

- 不是营销页、酷炫大屏或可视化展板。
- 不是把所有 AI 能力堆在一个 Tab 里。
- 不是让 AI 直接修改金额、证据、排班、结算或审计记录。
- 不是继续扩大 `components/reference-ui/ops-reference.jsx` 的内联样式和字符串路由边界。

### 是

- 一个高频运营工作台，面向 MCN 运营、项目经理、审核、财务和负责人。
- 以行动队列为主，以 AI 解释和草稿为辅。
- 以业务闭环为出口：招募、排班、报数、结算、审计、项目详情。
- 所有高风险动作都保留人工确认和结果反馈。

## 信息架构

### 1. 顶部壳层

沿用迁移包的经营舱壳层：

- 左侧固定导航，宽度 220-248px。
- 顶部 64-68px 工具栏，包含面包屑、通知、帮助、账号入口。
- 页面背景 `#f7f8fa`，主体卡片白底。
- 卡片圆角 6px，普通控件 4-6px。

当前旧入口可以先承载在 `warroom`，但视觉语言必须与迁移包收敛；长期路由化时，应按迁移包分拆到 App Router 页面，而不是继续把作战台塞进单个巨型组件。

### 2. 今日战情摘要

页面标题为“今日指挥台”或“智能作战台”，副标题说明数据更新时间、责任范围和排序规则。

摘要条只保留四个对行动有用的指标：

- 必须处理：今日需要人工介入的事项数。
- 高风险事项：命中风险规则或即将超时事项数。
- 影响金额/交付影响：金额、时长或外部交付影响。
- AI 已生成草稿：可审阅但未执行的 AI 产物数。

这些指标不得伪造环比或趋势。没有真实时序数据时不画趋势线。

### 3. 行动队列

第一屏主体是稳定表格或列表，不是大卡片瀑布流。推荐列：

| 列 | 内容 |
|---|---|
| 优先级 | 高 / 中 / AI 草稿 / 已分派，必须同时有文字和颜色 |
| 事项 | 业务语言描述，例如“3 条弱证据即将超时” |
| 影响 | 阻塞结算、影响交付时长、影响金额、影响对外沟通 |
| 证据来源 | `live_reports`、`ocr_jobs`、`settlement_batches`、`dashboard.queue` 等 |
| 负责人 | 运营、审核、财务、项目经理或具体人员 |
| 下一步 | 进入真实业务页面、打开抽屉、审阅草稿或确认动作 |

排序规则：

1. 即将超时且会阻塞下游闭环的事项优先。
2. 高风险金额、弱证据和结算锁定相关事项优先。
3. 影响当天直播交付的排班/主播缺口优先。
4. AI 生成产物只进入“待审阅”队列，不压过真实阻塞事项。

### 4. 右侧 AI 指挥助手

右侧不是聊天主舞台，而是行动队列的解释层和草稿层：

- 解释当前排序原因。
- 列出引用的数据范围和证据来源。
- 生成处理草稿、厂家简报草稿、复核清单草稿。
- 回答“为什么这项排第一”“这项会阻塞什么”“下一步要看哪个页面”。

AI 输出必须有边界：

- 可以推荐、解释、生成草稿、创建待确认任务。
- 不能直接锁定结算、修改金额、覆盖证据、删除数据、发送外部通知。
- 对金额、证据、结算和审计相关建议，默认显示“需人工确认”。
- AI 用到的上下文必须可见，包括当前项目、风险队列、报数队列、排班和结算批次。

### 5. 事项详情抽屉

点击行动队列行后打开详情抽屉或进入对应业务页。

详情抽屉包含：

- 事项标题、优先级、SLA。
- 影响链路：例如“弱证据 -> 报数审核 -> 结算锁定 -> 厂家交付包”。
- 证据列表：数据源、记录 ID、更新时间、可信度。
- AI 解释：为什么排这个优先级。
- 可执行动作：进入复核、查看候选、打开差异说明、审阅草稿。
- 审计说明：哪些动作会写审计日志。

## 数据映射

优先复用现有真实数据和 DTO：

- `dashboardHome.queue`、`dashboardHome.risks`、`dashboardHome.panels`：今日行动队列、风险和经营摘要。
- `projects`：项目状态、负责人、毛利和交付阶段。
- `tasks`：排班、直播中、异常、未开始和冲突。
- `reports`：报数审核、弱证据、OCR 结果和超时。
- `batches`：结算批次、金额差异、锁定和重开状态。
- `features/war-room/matching-engine.ts`：主播推荐、画像证据和撮合说明。
- `/api/ai/**`：AI 会话、项目复盘、简报和脚本草稿，但必须通过安全边界。

不得从页面直接拼接 Supabase 查询；页面应使用现有 feature service 或明确的 ViewModel adapter。

## 视觉规则

按迁移包执行：

- 背景：`#f7f8fa`。
- 卡片：`#ffffff`，边框 `#e5e6eb`，圆角 6px。
- 主色：`#165dff`。
- 成功：`#00b42a`。
- 警告：`#ff7d00`。
- 危险：`#f53f3f`。
- AI 辅助色可使用紫色，但只作为状态点缀，不主导页面。
- 普通文本、表格和表单以 12px 为主。
- 分区标题 14px，页面标题 22px，关键指标 28-36px。
- 不使用大面积深色渐变、装饰背景、浮动玻璃卡或营销式 hero。
- 图标正式实现使用 `lucide-react`，不引入 Iconify CDN。
- 若继续使用 Arco React，Arco CSS 必须保持 layered import，避免覆盖 Tailwind 工具类。

## 响应式

验收视口：

- 1920 x 1080
- 1440 x 900
- 1280 x 800
- 1024 x 768
- 768 x 1024
- 390 x 844

桌面：

- 左侧导航 + 主区域。
- 主区域为“行动队列 + 右侧 AI 指挥助手”两栏。
- 右栏宽度约 320px。

中等宽度：

- 行动队列保留主优先级。
- 右侧 AI 面板下移或折叠为抽屉。

移动端：

- 导航转顶部或底部入口。
- 摘要指标压缩为 2 列。
- 行动队列转为紧凑列表，每项显示优先级、事项、影响、下一步。
- AI 助手默认折叠，不遮挡主要操作。

## 状态设计

每个状态都必须可验收：

- 默认：有真实队列和真实摘要。
- 加载：表格骨架和摘要骨架高度稳定。
- 空数据：说明“当前无必须处理事项”，并给常用入口。
- 错误：显示可重试信息，不展示假数据。
- 无权限：说明当前账号无法查看哪些责任范围。
- 操作中：下一步按钮禁用并显示进行中。
- 已处理：队列项状态更新，保留可追踪反馈。

## 验收标准

产品验收：

- 第一屏不需要用户问 AI，就能知道今日优先处理事项。
- 每条事项都有证据来源、负责人和下一步。
- AI 排序解释能对应队列中的数据来源。
- 敏感动作必须人工确认。
- 点击下一步进入真实业务闭环，而不是停留在静态提示。

设计验收：

- 页面观感与迁移包 `operations.css` 一致。
- 不出现旧 `OverviewBoard` 的厚重渐变、超大装饰卡或概念化 AI 卡片。
- 表格、筛选、按钮、抽屉在目标视口无重叠、溢出和双滚动条。
- 文本不被按钮或卡片裁切。

工程验收：

- 不复制原型模拟数据进生产。
- 不引入 Iconify、Marked 或 DOMPurify CDN。
- 不新增跨业务全局 Provider。
- 不把完整页面包成单个 Client Component，除非交互确实需要。
- 不在本轮改 API、数据库、RBAC 或结算规则。

## 自审

### 方案强点

- 把“智能作战台”从 AI 展示页转回运营决策页，符合用户选择的 A：今日指挥。
- 继承迁移包的视觉语言，避免旧版概念卡和大屏风。
- AI 被放在解释、草稿和证据引用位置，不越过钱和证据的边界。
- 能兼容现有 `dashboardHome`、war-room API 和 AI 会话能力。

### 风险

- 如果短期仍在 `ops-reference.jsx` 内实现，容易继续增加巨型组件复杂度。
- 当前 `OverviewBoard` 已有大量自定义样式，迁移到新视觉需要防止半新半旧。
- 行动队列排序需要明确权威 ViewModel，否则前端可能重复推导业务优先级。
- AI 解释如果没有结构化 evidence，会退化成不可核验文本。

### 建议

下一步进入实施计划前，先确认两个边界：

1. 短期是否允许在旧 `warroom` 入口内先做视觉和信息架构收敛？
2. 是否同步启动迁移包建议的 App Router 新壳层基础阶段？
