# 2026-06-30 可商用产品功能完整度审计

审计对象：经营舱 / Constella 当前仓库  
审计日期：2026-06-30  
审计口径：以“能否作为可商用 SaaS 产品交付客户”为标准，不只看代码是否存在，也看真实入口、定价、登录、角色闭环、支付与运营可验收性。

## 1. 总结结论

当前产品已经具备较强的工程底座和业务闭环雏形：P1/P2/P3/P4/P5 相关服务、API、数据库契约和回归测试覆盖很广，全量测试通过 `266 passed | 1 skipped`，共 `1306 passed | 4 skipped`。从“内部验收 / 设计伙伴试点”角度，产品可继续推进。

但按“可商用产品”标准，当前不建议直接正式售卖。主要原因不是主线业务想法缺失，而是有几个会直接影响客户进入和付费认知的入口级问题：

1. 主播移动端登录入口 `/m/login` 存在重定向循环，主播端未登录用户无法进入登录页。
2. 套餐页将基础版、专业版、旗舰版都展示为 `¥0 / 月`，商业价格展示不可信。
3. 真实支付、发票、税务、对账、外部通知、生产 AI provider、客户成功与运营后台仍需要商业化闭合。
4. 认证后完整浏览器级业务流没有在本次无账号状态下可截图验收，仍需建立稳定演示/试用数据和端到端验收账号。

综合判断：

| 维度 | 当前状态 | 商用判断 |
| --- | --- | --- |
| 工程与测试底座 | 成熟，覆盖广 | 可作为继续商业化的基础 |
| 核心业务模型 | 已形成“项目 -> 主播 -> 准入 -> 排班 -> 报数 -> 结算 -> 治理 -> 套餐”闭环 | 可进入试点 |
| 未登录入口 | 登录、注册、定价基本存在 | 主播移动端入口阻断，必须修 |
| 客户付费认知 | 有 pricing 与 billing 模块 | 价格展示错误，不能正式销售 |
| 付费闭环 | 有 P6/payment 结构和 mock provider 迹象 | 真实支付/发票/对账未到正式商用 |
| 运营交付 | 文档齐、测试多 | 仍缺演示数据、客户 onboarding、支持闭环 |

当前商业完整度估计：`65%`。  
可进入“受控试点 / 设计伙伴”阶段；距离正式商业发布仍需 2-4 周集中补齐入口、定价、试用闭环、支付沙箱、监控与端到端验收。

## 4. P0/P1 风险清单

### P0-1 主播移动端登录入口不可用

影响：主播无法从手机登录，直接切断“任务、开播、下播、报数、截图、结算查看”这条外部用户链路。  
建议：

- 在 `middleware.ts` 中排除 `/m/login`，必要时也排除 `/m/login/*`。
- 增加测试：`/m/login` 无会话时应返回 200，不应 307。
- 增加浏览器 smoke：未登录访问 `/m/tasks` -> `/m/login?next=/m/tasks`，随后登录后回到 `/m/tasks`。

### P0-2 Pricing 展示全 0 元

影响：正式售卖前会破坏客户信任，也会干扰销售、合同与试用升级路径。  
根因：`20260619120000_default_billing_subscription.sql` 用 0 元 seed 标准套餐；后续 P6 迁移写入真实价格时 `on conflict (code) do nothing`，旧数据不会被修正。  
建议：

- 对标准套餐使用受控 upsert，明确更新 `monthly_price_cents`、`annual_price_cents`、额度与 features。
- pricing 页面优先读取 `billing_plan_prices` 当前 active 价格版本，避免直接依赖旧 `billing_plans` 金额字段。
- 增加测试：基础版/专业版/旗舰版不能同时为 0，除非显式处于 `demoPricing=true`。

### P1-1 试用注册后的首日成功路径不够可证

`/signup` 文案承诺“无需人工审核，注册后立即创建组织并进入产品”，但商用要求不止能注册，还要让客户 10 分钟内看到价值。  
建议：

- 注册后强制进入 onboarding，并提供“创建首个项目 / 导入示例 / 邀请主播 / 查看演示闭环”三种路径。
- 不把演示数据写进源码 seed，但允许按组织生成可删除的 sample workspace。
- 增加端到端验收：注册 -> onboarding -> 创建项目 -> 添加主播 -> 排班 -> 报数 -> 审核 -> 结算预览。

### P1-2 第三方登录展示“待配置”

经营端和主播端登录页均展示微信/飞书入口，但状态为待配置。  
建议：

- 未配置时不要展示为同等优先级按钮，改为灰阶说明或隐藏。
- 正式商用前至少配置一个企业常用登录方式，或明确只支持账号密码/手机号。

### P1-3 真实支付与财务运营闭环仍需正式上线

当前已有 billing、order、webhook、invoice、reconciliation 等结构，但正式商用要求：

- 支付 provider 沙箱和生产环境可切换。
- webhook 签名、幂等、重复通知和异常补偿完成验收。
- 发票申请、开票状态、退款、对账差异处理有运营台。
- 订阅升级/降级/续费/逾期只读均有浏览器级验收。

### P1-4 端到端浏览器验收需要补齐

测试非常多，但仍能漏掉 `/m/login` 这种入口级问题。  
建议把关键验收从“组件/服务测试”补到“真实路由浏览器烟测”：

- 未登录入口矩阵：`/login`、`/signup`、`/pricing`、`/m/login`、`/console`、`/m/tasks`、`/desktop`。
- Owner 业务闭环：注册/登录 -> 项目 -> 主播 -> 排班 -> 报数审核 -> 结算 -> 导出。
- Streamer 业务闭环：登录 -> 查看任务 -> 开播 -> 下播 -> 上传截图 -> 提交报数 -> 查看收益。
- Billing 闭环：选择套餐 -> 创建订单 -> 支付回调 -> 订阅生效 -> 额度变化。

## 5. 后续产品方案

### Phase 0：商用阻断修复，1-3 天

目标：让客户入口和价格展示先可信。

必须完成：

- 修复 `/m/login` 重定向循环。
- 修复 pricing 标准套餐价格，建立价格版本读取策略。
- 隐藏或弱化未配置的微信/飞书登录入口。
- 增加未登录入口浏览器 smoke。
- 把 `middleware.test.ts` 增加 `/m/login` 放行用例。

验收标准：

```text
/login       200
/signup      200
/pricing     200，非免费套餐显示真实价格
/m/login     200
/m/tasks     307 -> /m/login?next=/m/tasks，不循环
/console     307 -> /login?next=/console
/desktop     307 -> 合理登录入口
```

### Phase 1：试用转激活闭环，1-2 周

目标：新客户不用人工陪跑，也能在 10 分钟内跑通核心价值。

必须完成：

- 注册后 onboarding 串起核心步骤，并记录漏斗事件。
- 新组织支持生成“可删除演示工作区”或“引导式首项目”。
- 项目、主播、排班、报数、结算的首个空态都给出明确下一步。
- 经营端和主播端分别有角色专属登录/跳转体验。
- 建立一套稳定验收账号和浏览器 smoke 数据。

验收标准：

```text
新 owner 注册后 10 分钟内能完成：
创建项目 -> 添加/导入主播 -> 创建任务 -> 看到报数/结算示例 -> 理解下一步如何正式使用
```

### Phase 2：正式收费闭环，2-4 周

目标：从“能演示收费能力”升级为“能真实收钱、开票、对账、处理异常”。

必须完成：

- 接入真实支付 provider 沙箱，跑通订单、回调、订阅状态变更。
- 完成发票申请、开票状态、退款、对账差异运营台。
- 套餐升级/降级、加量包、功能加购、逾期只读都可浏览器验收。
- 价格、权益、额度变更走版本化与审计，不靠手改数据库。

验收标准：

```text
客户可以从 pricing 选择套餐并完成沙箱支付；
支付成功后权益立即生效；
逾期/取消后写动作被拦截但历史结算和审计可读；
财务可查订单、发票、退款、对账结果。
```

### Phase 3：生产运营化，4-8 周

目标：降低真实客户使用时的支持压力和故障风险。

必须完成：

- 外部通知：企业微信/飞书优先，短信/邮件按客户要求补齐。
- 生产监控：登录失败、支付失败、OCR/AI 失败、导出失败、webhook 失败。
- 客户支持入口：帮助中心、操作教程、故障反馈、问题追踪。
- 权限治理：SSO、二次验证、成员邀请、角色变更审计。
- AI 生产化：provider 配置、成本上限、灰度指标、人工复核。

验收标准：

```text
连续 2 周试点运行无 P0；
关键任务成功率 >= 99%；
支付/导出/报数/结算失败均有可定位日志和运营处理入口；
客户无需研发介入即可完成常规账号、套餐、发票和数据导出问题。
```

## 6. 商业发布门槛

正式商业发布前建议设置以下硬门槛：

1. 入口健康：所有公开入口和受保护入口的跳转矩阵通过浏览器 smoke。
2. 价格可信：pricing、订单、订阅、发票使用同一套价格版本。
3. 试用可激活：新客户能自助跑通首个闭环。
4. 角色可用：owner、ops、finance、streamer 至少各有一条浏览器级黄金路径。
5. 支付可追溯：订单、支付、webhook、退款、发票、对账全链路有审计。
6. 数据不泄漏：主播和外部分享端不暴露厂家应收、毛利、成本和内部风险备注。
7. 运营可恢复：导出、OCR、AI、支付、通知失败都有重试或人工处理方案。
8. 监控可发现：P0 入口问题、支付失败、队列堆积、AI/OCR 异常能在生产监控中暴露。

## 7. 建议优先级

最高优先级：

1. 修 `/m/login`。
2. 修 pricing 价格源。
3. 增加入口路由浏览器 smoke。
4. 建立可删除的试用演示数据和稳定验收账号。

第二优先级：

1. 真实支付 provider 沙箱。
2. 发票/退款/对账运营台。
3. 外部通知。
4. 角色路径 E2E。

第三优先级：

1. SSO/2FA/账号安全。
2. AI provider 生产配置和成本治理。
3. 大客户私有化、审计留存、权限审批。

## 8. 最终判断

经营舱不是“功能还没起来”的状态。相反，它的后端、权限、审计、结算、AI、商业化底座已经明显厚于普通 MVP。

真正要跨过的坎，是从“研发验收完整”转成“客户自助可用、销售可解释、财务可闭合、运营可恢复”。当前最该做的不是继续扩更多大模块，而是用商业化标准收紧入口、定价、试用、支付、浏览器验收和运营闭环。
